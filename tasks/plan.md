# План реализации локального MVP MyBooking

Статус: карта работ согласована владельцем 05.10.2026; параметры требований уточнены в PDR v1.5. Основание: [PDR](../docs/PDR.md), [ADR-001](../docs/ADR-001.md), [ADR-002](../docs/ADR-002.md) и [онтология](../docs/ONTOLOGY.md). Детали — в [пронумерованных задачах](todo.md); порядок работы агентов — в [workflow](workflow.md). План не разрешает начинать код: владелец проекта потребовал отдельного согласия.

## Последовательность и зависимости

| Этап | Модуль | Зависит от | Результат и контроль |
| --- | --- | --- | --- |
| 0 | Контракт и каркас репозитория | PDR, ADR | Четыре npm workspace, TypeSpec → OpenAPI 3.1, строгая конфигурация TypeScript; AC-22. |
| 1 | `identity` и `privacy` | Контракт | Отдельные Backend- и Frontend-задачи для входа, проверки гостя, согласия и cookie; AC-01/02/20/21. |
| 2 | `availability` | `identity` | Отдельные Backend- и Frontend-задачи для расписания и слотов; границы и DST; AC-03/04/11. |
| 3 | `bookings` | `identity`, `privacy`, `availability` | Отдельные Backend- и Frontend-задачи для заявки, решения эксперта, конфликтов и изменения расписания; AC-05–10/12. |
| 4 | `notifications` | `bookings` | Постоянная очередь, реальные письма, напоминания и ICS; AC-13/14/16/18. |
| 5 | `updates` | Сервер и интерфейс бронирований | Раздельные задачи SSE на сервере и в интерфейсе; AC-17. |
| 6 | `operations` | Собранные сервер и интерфейс | Область работ, не отдельный агент: Backend-задачи Docker Compose, тома, backup/restore и CI; Тестировщик проводит сквозную приёмку; AC-19/23. |

Контракты API и данных каждого этапа фиксируются перед его кодом. Frontend-задача может стартовать после стабильного интерфейса соответствующей Backend-задачи; ждать завершения всего сервера не требуется. Для каждой задачи действует цикл [TDD workflow](workflow.md): красный тест Тестировщика → код одного разработчика → независимое ревью → зелёная проверка Тестировщика → приёмка координатором. Реальные SMTP-письма проверяются вручную с рабочими учётными данными. Публикация образа, `git push` и деплой требуют отдельного разрешения; готовый workflow их не выполняет сам по себе.

## Интерфейсы модулей

- `identity` выдаёт серверу подтверждённый email и права эксперта либо гостя на конкретную заявку. Остальные модули не читают коды и токены напрямую.
- `privacy` сообщает версию и факт согласия для действия. Подробности хранения и cookie остаются внутри модуля.
- `availability` принимает эксперта, подтверждённый email гостя, длительность и переданные часы; возвращает доступные моменты и причину отказа без HTTP или SQL.
- `bookings` принимает команды создания и переходов; проверяет правила и атомарно записывает состояние, закрытие конфликтов и задачи. Вызовы SMTP и SSE выполняются после commit.
- `notifications` получает зафиксированные задачи, готовит письмо или ICS и сохраняет результат попытки. Доставка не меняет подтверждённый статус встречи.
- `web` пользуется публичным контрактом, не внутренними таблицами. `operations` собирает и запускает тот же сервер с сохранением SQLite между перезапусками.

## Риски и контрольные точки

| Риск | Проверка до перехода |
| --- | --- |
| Разные трактовки времени и DST | Модульные тесты полуоткрытых интервалов, границ 24 часа/3 часа/30 суток и двух ветвей повторяющегося часа. |
| Двойное подтверждение или утечка данных гостя | Интеграционные тесты с отдельными подключениями SQLite и запросами чужих записей. |
| Потеря письма или повтор после сбоя | Тесты очереди и восстановления; ручная отправка Gmail отмечается отдельно. |
| Несовпадение TypeSpec и Fastify | Генерация OpenAPI в CI и контрактные тесты по документированным ответам. |
| Потеря SQLite при пересоздании контейнера | Проверка сохранения данных в томе, SQLite Backup API и восстановления при остановленном приложении. |
| Публичная эксплуатация | После локальной приёмки отдельно решить домен, HTTPS, секреты и правовые обязанности. До этого не объявлять сервис развёрнутым. |

## Готовность

Модуль считается готовым, когда сценарии PDR реализованы, типы и линтер проходят, относящиеся тесты зелёные, документация запуска соответствует проверенным командам. Весь MVP готов после проверки локального контейнерного пути эксперта и гостя, сохранности SQLite, настоящего SMTP и импортируемого ICS. Внешние действия и недоступные проверки перечисляются в итоговом отчёте без заявления об успехе.
