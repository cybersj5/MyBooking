# TDD pipeline мультиагентной разработки

Статус: согласован владельцем проекта 05.10.2026. Код MVP, запуск исполнителей для его написания, коммиты, `git push`, публикация образа и деплой требуют разрешений по AGENTS.md.

## Роли

| Роль | Ответственность |
| --- | --- |
| Координатор | Основной агент чата фичи. Проверяет зависимости и требования, назначает задачу, разводит файлы, принимает итог и обновляет `tasks/todo.md`. |
| Backend-разработчик | Реализует одну назначенную серверную задачу после красного теста. Пишет серверный код, SQL, контракт или инфраструктуру по области задачи. |
| Frontend-разработчик | Реализует одну назначенную интерфейсную задачу после красного теста. Пишет только свою часть интерфейса. |
| Ревьюер | Независимо сверяет код разработчика с PDR, ADR, интерфейсом и критериями приёмки. Возвращает замечания разработчику через координатора. |
| Тестировщик | До кода пишет проверку фичи и подтверждает ожидаемое падение. После ревью запускает её и нужную регрессию, сообщает координатору результат. При провале возвращает задачу разработчику через координатора. |

Пять ролей не означают пять одновременно работающих агентов. В этом чате доступны четыре одновременных места вместе с координатором, то есть до трёх активных субагентов. Координатор проверяет фактическую ёмкость при каждом запуске. Backend и Frontend подключаются только к своим задачам; Ревьюер и Тестировщик работают по очереди на контрольных этапах. Отдельного агента Operations нет: задачи 022–024 выполняет Backend-разработчик.

## Цикл одной задачи

1. **Подготовка.** Координатор выбирает готовый номер задачи, сверяет указанные в ней разделы PDR/ADR/онтологии и для Frontend дизайн-документы, фиксирует ожидаемое поведение, область файлов и одного разработчика: Backend **или** Frontend. Новое требование сначала согласуется и записывается в PDR.
2. **Red.** Тестировщик пишет тест по критерию приёмки и запускает его до реализации. Ожидаемое падение с конкретной причиной передаётся координатору и разработчику. Если тест уже проходит или падает по неверной причине, Тестировщик исправляет тест.
3. **Green, реализация.** Назначенный разработчик пишет минимальный код, достаточный для прохождения теста, и выполняет локальные проверки своей области. Он передаёт координатору изменённые файлы, результаты проверок и ограничения. Второй разработчик эту задачу не меняет.
4. **Ревью.** Ревьюер проверяет соответствие указанным разделам PDR/ADR/онтологии, доступ, ошибки, инварианты и достаточность теста. Для Frontend он также сверяет сценарий и визуальные правила `docs/design/DESIGN.md` и контекст `docs/design/PRODUCT.md`. При расхождении приоритет у PDR и принятых ADR. Замечания возвращаются тому же разработчику. Исправленный код снова проходит ревью.
5. **Проверка.** После одобрения Ревьюера Тестировщик запускает тест фичи и относящуюся регрессию. Для Frontend он проверяет клавиатуру, темы, адаптивность и состояния по дизайн-документам. Провал возвращает задачу разработчику через координатора; после исправления повторяются ревью и проверка.
6. **Приёмка.** Тестировщик сообщает координатору, что именно прошло, что не проверено и почему. Только координатор отмечает задачу выполненной и открывает зависящие от неё задачи.

Рефакторинг внутри задачи допускается после зелёного теста; после него снова проходят ревью и проверка. Тесты должны проверять поведение и критерии PDR, а не повторять строки реализации. Для инфраструктурной задачи, где красный автоматический тест неуместен, Тестировщик заранее фиксирует воспроизводимую падающую проверку или недостающий артефакт.

## Параллельность и владение файлами

- Разные задачи могут идти одновременно, только если зависимости закрыты и файлы не пересекаются. Фронт и бэк одной возможности живут в отдельных пронумерованных задачах; у каждой один разработчик.
- `contract/main.tsp`, `contract/openapi.yaml`, `server/src/repository.ts`, корневые конфигурации и документы PDR/ADR имеют одного назначенного владельца на время задачи. Другой агент запрашивает передачу у координатора.
- Тестировщик владеет тестами текущей задачи. Разработчик не исправляет тест для получения зелёного результата без согласования с Тестировщиком и координатором.
- Ревьюер не правит код разработчика в ходе ревью. Он возвращает конкретные замечания с привязкой к требованию или критерию.
- Задачи 020 и 021 разделяют SSE: серверный контракт и доступ сначала, интерфейс после него. Задачи 022–024 Backend выполняет после появления нужных модулей.
- Исполнители используют отдельные временные SQLite-файлы и не запускают параллельное форматирование всего репозитория или миграции одной БД.

При необходимости координатор создаёт изолированные worktree для независимых задач. В общем checkout действует исключительное владение файлами. Коммиты и `git push` выполняются только по прямой просьбе владельца проекта.

## Передача и отчёт

Каждый переход сопровождается коротким сообщением: номер задачи, AC, изменённые файлы, выполненная команда и результат, блокирующий вопрос. Успех автоматических тестов не заменяет ручную проверку Gmail, импорт ICS или запуск контейнера. Недоступные проверки отмечаются как непроверенные; Тестировщик не объявляет всю фичу завершённой, если обязательный критерий остался без проверки.
