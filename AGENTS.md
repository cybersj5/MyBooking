# AGENTS.md — правила работы в MyBooking

Инструкции применяются ко всему репозиторию.

## Описание проекта

MyBooking — учебный веб-MVP для бронирования индивидуальных встреч с ручным подтверждением. Пользователь настраивает расписание, делится личной ссылкой, принимает заявки и подтверждает встречи. Каждый зарегистрированный пользователь может быть организатором и гостем; роль определяется конкретной встречей.

Первый MVP включает вход по одноразовому email-коду, расписание и исключения, учёт часовых поясов, заявки и встречи, предотвращение пересечений у обоих участников, реальные email-уведомления, экспорт ICS и ручные backup/restore.

Приложение запускается вручную на одном компьютере и работает только пока запущен процесс. Серверы слушают только loopback. Публичный деплой, PostgreSQL и Телемост отложены. Оплата, команды, групповые встречи, каталог пользователей и синхронизация внешних календарей не входят в MVP.

На момент создания этого файла в репозитории есть только документация. Ниже описан выбранный стек для реализации, а не уже работающее приложение. Команды установки, сборки, запуска и тестирования следует документировать по мере их появления; не выдавать предполагаемые команды за проверенные.

## Документация и порядок работы

- [docs/PDR.md](docs/PDR.md) — требования, границы продукта и критерии приёмки.
- [docs/ADR-001.md](docs/ADR-001.md) — принятые архитектурные решения.
- [docs/ONTOLOGY.md](docs/ONTOLOGY.md) — понятия и отношения предметной области; это не схема БД и не самостоятельное утверждение предложений PDR.

Перед изменениями читать относящиеся к задаче разделы. Отличать принятые решения от предложений и открытых вопросов. При противоречии, влияющем на задачу, уточнять решение у пользователя, а не молча выбирать трактовку.

Следовать SDD: спецификация сценариев и инвариантов → контракты API и данных → план → код → проверки с привязкой к критериям приёмки. После согласования изменения требований обновлять PDR, сохраняя ID и связанные критерии; синхронизировать затронутые понятия в онтологии и сценарии в спецификациях. Архитектурные изменения фиксировать в ADR. Не дублировать всю бизнес-спецификацию в этом файле.

## Скиллы Codex

Использовать установленные скиллы Matt Pocock по задаче, сохраняя порядок SDD и правила этого файла:

- `domain-modeling` — при уточнении понятий онтологии и изменении ADR.
- `research` — при проверке спорных деталей библиотек, времени, SQLite, SMTP и ICS по первичным источникам.
- `codebase-design` — при проектировании границ модулей и их интерфейсов.
- `tdd` — при реализации проверяемых бизнес-правил и интеграционных сценариев; особенно для DST, конкурирующих бронирований и прав доступа.
- `diagnosing-bugs` — при сложных сбоях и регрессиях.
- `code-review` — при проверке изменений относительно требований, ADR и соглашений по коду.
- `prototype` — когда нужно проверить спорную модель состояний или вариант интерфейса до реализации.

По прямому вызову пользователя применять `to-spec` для спецификации сценария, `to-tickets` для разбиения на небольшие задачи и `implement` для работы по согласованной спецификации. Перед первым использованием этих скиллов настроить их через `setup-matt-pocock-skills` с учётом существующих PDR, ADR и онтологии. Требования к русскому языку документации и запрет на коммиты без прямой просьбы действуют также при работе со скиллами.

## Стек

| Область | Выбор |
| --- | --- |
| Язык и среда | TypeScript со strict, поддерживаемая Node.js LTS |
| Пакеты | npm, фиксируемый в репозитории package-lock.json |
| Сервер | Fastify, JSON Schema для входных и выходных контрактов |
| Интерфейс | React + Vite, CSS, стандартные браузерные API |
| Хранилище | SQLite, better-sqlite3, Drizzle ORM; миграции через Drizzle Kit |
| Время | @js-temporal/polyfill за отдельным модулем времени |
| Почта | Nodemailer, реальный Gmail SMTP |
| Обновления | SSE для сигналов обновления, HTTP для команд |
| Проверки | Vitest, Fastify inject, Playwright |
| Качество кода | ESLint и Prettier |

Архитектура — модульный монолит: один сервер Node.js обслуживает API, собранный интерфейс, SSE и постоянную очередь фоновых задач в SQLite. В разработке Vite работает отдельным процессом и проксирует API/SSE.

При инициализации фиксировать совместимые стабильные версии и версию Node.js, проверять установку нативного better-sqlite3 на Windows. Предлагаемая в ADR структура: `apps/web`, `apps/server`, `packages/contracts`; она пока не создана. Серверные области: `auth`, `profiles`, `availability`, `bookings`, `notifications`, `calendar-export`.

## Соглашения по коду

- Общение с пользователем, включая вопросы, сообщения о ходе работы и итоговые отчёты, — на русском языке.
- Вся документация — на русском языке. Комментарии в коде — только однострочные, на русском языке; объясняют причину или нетривиальное ограничение. Развёрнутые объяснения выносить в документацию.
- Пользовательские тексты интерфейса, ошибок и писем, а также текстовые поля ICS — на русском языке согласно UI-02. Идентификаторы, имена файлов и модулей, названия тестов, сообщения коммитов и технические логи — на английском.
- Использовать отступ в 2 пробела; форматирование поручать Prettier, статические проверки — ESLint. Общие настройки хранить в репозитории.
- Функции и переменные именовать в `camelCase`, типы и React-компоненты — в `PascalCase`.
- Соблюдать TypeScript strict. Не отключать проверки типов или линтера для сокрытия ошибки; исправлять причину.
- Отделять бизнес-правила от HTTP, БД, почты и интерфейса. Расчёт доступности делать чистым модулем с передаваемыми часами для тестов.
- Проверять входные данные и права на каждый объект на сервере. Клиентские проверки не заменяют серверные.
- Общие контракты не должны экспортировать клиенту схему БД, серверную конфигурацию или секреты.
- Предпочитать простые решения в рамках текущего MVP. Не создавать универсальные абстракции и слой репозиториев для всех таблиц без потребности конкретных сценариев.

## Обязательные ограничения реализации

- UTC-моменты хранить как epoch milliseconds, часовые пояса — как IANA ID. Недельные часы и исключённые даты хранить как локальные значения. Границы интервалов, сроки и DST реализовывать по PDR и ADR, без молчаливого сдвига несуществующего времени.
- Все изменения заявок, занятости, расписания и пояса проводить через общий транзакционный протокол с `BEGIN IMMEDIATE` до чтения условий записи. Занятость проверять у обоих участников независимо от роли.
- Подтверждение, закрытие пересекающихся заявок и создание фоновых задач фиксировать атомарно. В синхронных транзакциях better-sqlite3 запрещены `await` и сетевые вызовы. Внешние эффекты и SSE выполнять после commit.
- Постоянные задачи сохранять в SQLite; таймеры в памяти не заменяют очередь. Соблюдать идемпотентность команд, дедупликацию внутренних эффектов и политику восстановления из ADR.
- Ошибка отправки почты не откатывает подтверждённую встречу. Не обещать ровно однократную доставку SMTP или напоминания при выключенном приложении.
- В пользовательском режиме использовать реальные email-коды и SMTP. Подмена транспорта допустима только в автоматических тестах; они не отправляют реальные письма.
- Секреты брать из локального окружения. Не хранить в Git `.env`, файлы БД, WAL/SHM и резервные копии. В `.env.example` — только имена и безопасные примеры.
- Не логировать секреты, коды входа, токены и содержимое писем. Не раскрывать чужие сведения через API, SSE или интерфейс. Не обходить авторизацию, проверки Origin и CSRF.
- Не копировать один активный файл SQLite как резервную копию: использовать SQLite Backup API. Восстановление выполнять при остановленном приложении по процедуре ADR; отправку восстановленной очереди возобновлять только явно.
- Не добавлять в первый MVP Телемост, его OAuth-настройки, задачи создания конференций или вымышленные успешные видеоссылки.

## Самостоятельность и согласования

В рамках поставленной задачи самостоятельно выполнять обычные изменения кода и документации, исправления и необходимые проверки, соблюдая принятые требования и архитектуру.

Предварительно согласовывать с пользователем:

- изменение требований, границ MVP или архитектуры;
- добавление зависимостей вне выбранного стека;
- удаление данных;
- публикацию, деплой и `git push`.

Коммиты создавать только по прямой просьбе пользователя. Не отменять и не перезаписывать чужие изменения, не относящиеся к задаче. Не расширять задачу несвязанными рефакторингами.

## Проверки и отчёт о результате

Проверять изменения средствами, соответствующими их риску: чистую логику — Vitest, API — Fastify inject, пользовательские сценарии — Playwright. Для времени проверять граничные моменты и DST; для бронирований — конкурирующие операции через отдельные подключения к временной SQLite; для доступа — изоляцию пользователей. Полный перечень сценариев и критериев приёмки находится в PDR и ADR.

После появления конфигурации запускать относящиеся к изменению проверки типов, линтер, тесты и сборку. Исправлять обнаруженные ошибки в рамках задачи. В отчёте указывать, что изменено, что действительно проверено и какие ограничения остались.

Не объявлять тесты, запуск, доставку писем, импорт ICS или интеграции успешными без фактической проверки. Автоматические тесты с подменённым транспортом не заменяют ручную приёмку с реальным Gmail. Не проверенные из-за отсутствия доступа сценарии явно отмечать как непроверенные.
