# MyBooking — PDR: требования к продукту

Версия: 1.5. Дата: 05.10.2026. Формат: документ требований к продукту для Specification-Driven Development (SDD).

Статус: результаты продуктового и архитектурного интервью зафиксированы; см. [ADR-001](ADR-001.md) и [ADR-002](ADR-002.md). Технические предложения и открытые вопросы явно отделены от согласованных требований. Документ не означает, что приложение уже реализовано или интеграции проверены вживую.

## 1. Цель и границы продукта

MyBooking — учебный веб-MVP для бронирования индивидуальных созвонов с ручным подтверждением. Пользователь делится личной ссылкой, получает заявки, подтверждает удобную встречу и отправляет участникам сведения о ней.

Эксперт регистрируется и настраивает личную страницу бронирования. Гость открывает её без аккаунта. Один эксперт вправе забронировать встречу у другого как гость; роль определяется конкретной встречей. Решение о госте без аккаунта от 05.10.2026 заменяет прежнее требование обязательного входа каждого участника.

Ценность: согласование времени без переписки, отсутствие двойного бронирования, единое расписание, email-уведомления, ICS и необязательная интеграция с Телемостом.

Успех MVP: эксперт входит по email-коду и настраивает расписание; гость без аккаунта подтверждает адрес кодом, подаёт заявку и получает письмо; эксперт подтверждает одну из пересекающихся заявок; другие гости получают отказ с предложением выбрать другое время. Подтверждённый интервал повторно не бронируется. Письма отправляются через реальный сервис, ICS импортируется, контейнер воспроизводимо запускается. Телемост отложен на следующий этап.

Не входят: оплата, каталог пользователей, команды и распределение заявок, групповые встречи, синхронизация внешних календарей, полноценные календарные приглашения и их обновления, ручной ввод ссылки, мультиязычность, имитация внешних интеграций. Расширенная админка, SSO и Телемост — следующие этапы. Сам деплой начинается после локальной приёмки MVP; подготовка контейнера и CI входит в MVP. Промышленный SLA не установлен.

## 2. Пользователи и доступ

| ID | Согласованное требование |
| --- | --- |
| AUTH-01 | Эксперт регистрируется и входит по одноразовому коду на email, без пароля. |
| AUTH-02 | При первом входе эксперта обязательны имя и выбранный часовой пояс; их можно менять в профиле. |
| AUTH-03 | Каждый эксперт получает личную ссылку с автоматически созданным уникальным идентификатором. |
| AUTH-04 | Гость просматривает свободные слоты по личной ссылке без регистрации и входа. Общего каталога нет. |
| AUTH-05 | Гость видит только доступность эксперта и свою конкретную заявку по защищённой ссылке; чужие имена, темы и детали недоступны. |
| AUTH-06 | Каждый эксперт настраивает собственное расписание и может подать заявку другому эксперту как гость. |
| AUTH-07 | Перед созданием заявки гость подтверждает владение email одноразовым кодом. Это не создаёт аккаунт. После подачи ему отправляется защищённая ссылка для просмотра и допустимых действий со своей заявкой. |
| AUTH-08 | Код эксперта и гостя действует 10 минут и допускает не более 5 неверных попыток. Новый код аннулирует прежний для того же адреса и действия. Просроченный, использованный, заменённый или исчерпавший попытки код не принимается. |
| AUTH-09 | Сессия эксперта действует 30 дней без продления от активности. Выход отзывает её немедленно. |
| AUTH-10 | Гостевая ссылка действует 30 дней. После истечения гость повторно подтверждает тот же email кодом и получает новую ссылку только на свою заявку. Старый токен не даёт доступа. |
| AUTH-11 | Для сопоставления занятости email приводится к нижнему регистру и очищается от пробелов по краям. Точки, `+`-метки и другие особенности провайдера не переписываются. |
| AUTH-12 | Код можно запрашивать не чаще одного раза в 60 секунд на email, не более 5 раз в час на email и 20 раз в час на IP. Ответ о лимите не раскрывает существование аккаунта. |
| AUTH-13 | После правильного кода аккаунт эксперта создаётся сразу. Пока имя и IANA-пояс не заполнены, эксперт может только заполнить профиль или выйти; повторный вход продолжает настройку. |
| AUTH-14 | Подтверждение email гостя действует 10 минут после проверки кода, однократно и только для выбранного эксперта. Оно погашается при успешном создании заявки; ошибка проверки заявки не расходует подтверждение. Повтор успешной команды с тем же ключом идемпотентности возвращает прежний результат. |
| AUTH-15 | Для восстановления гостевой ссылки запрашиваются ID заявки и email. Внешний ответ одинаков для существующей, чужой и отсутствующей заявки; код отправляется только на сохранённый email подходящей заявки. После успешной проверки кода выдаётся новая ссылка, а прежняя отзывается. Сам запрос восстановления действующую ссылку не отзывает. Ответ о принятии запроса не утверждает доставку письма. |

Согласовано: бронирование у самого себя запрещено, в том числе при совпадении подтверждённого email гостя с email эксперта. Предложение реализации: после входа эксперта возвращать его на исходную личную ссылку.

## 3. Правила времени и доступности

| ID | Правило |
| --- | --- |
| TIME-01 | Еженедельное расписание, несколько интервалов на каждый день недели. Отдельные даты можно полностью исключить. |
| TIME-02 | Длительность на выбор гостя: 15, 30 или 60 минут. Шаг начала — 15 минут. |
| TIME-03 | Встреча целиком помещается в интервал доступности организатора. Перерыв между встречами не требуется. |
| TIME-04 | Заявка подаётся минимум за 24 часа до начала. Горизонт бронирования — 30 дней. |
| TIME-05 | Подтверждение допускается не позднее чем за 3 часа до начала; необработанная заявка затем истекает. |
| TIME-06 | Гость отменяет встречу не позднее чем за 3 часа до начала. Организатор — в любой момент до начала. |
| TIME-07 | Подтверждённые встречи блокируют время эксперта и гостя. Для гостя совпадение определяется по подтверждённому email, включая его встречи у других экспертов. |
| TIME-08 | Подтверждённо занятый у любого участника интервал нельзя повторно забронировать. Проверка повторяется на сервере при подаче и подтверждении. |
| TIME-09 | Ожидающие заявки не занимают время: несколько гостей могут запросить один интервал. Число заявок и будущих встреч не ограничено бизнес-правилом. |
| TIME-10 | Эксперт подтверждает одну заявку на пересекающийся интервал. В той же транзакции закрываются все пересекающиеся ожидающие заявки обоих участников; гостям сообщают об отказе и предлагают выбрать другое время. |
| TIME-11 | Эти параметры общие для всех; организатор не изменяет длительности, шаг, горизонт и сроки. |
| TIME-12 | Расписание задаётся в часовом поясе эксперта; гость видит время в выбранном им поясе с явным обозначением. |
| TIME-13 | Смена пояса сохраняет часы еженедельного расписания, но не фактическое время уже созданных заявок и встреч и ничего автоматически не отменяет. |

Точная семантика времени (границы, DST и смена пояса согласованы в ADR-интервью; способы хранения закреплены в ADR-001):

- Время хранится как UTC-момент, пояс — IANA-идентификатор. Серверное время авторитетно.
- Интервалы полуоткрытые: [начало, конец). Встречи 10:00–10:30 и 10:30–11:00 не пересекаются.
- Нижняя граница подачи включительна: start >= now + 24 часа. Верхняя: start <= now + 30 суток. Горизонт означает ровно 30 × 24 часа и ограничивает начало встречи.
- Ровно за 3 часа подтверждение и отмена гостем разрешены; при меньшем остатке — запрещены. Истечение определяется этой проверкой, даже если фоновая задача ещё не обработала запись.
- Начала выравниваются на :00, :15, :30, :45 по времени организатора. Невалидные интервалы расписания отклоняются.
- Свобода гостя определяется подтверждёнными встречами по подтверждённому email. Если гость также эксперт, собственные часы приёма заявок не ограничивают его участие у другого эксперта.
- Несуществующее локальное время при DST пропускается; повторяющийся час даёт два варианта с разными UTC-моментами и явным смещением. Длительность считается в фактических минутах; вся встреча должна попадать в доступность.
- Интервалы через полночь задаются двумя частями; 24:00 допустимо как конец дня. TIME-03 сохраняется: встреча помещается в одну часть.
- При смене пояса исключённые даты сохраняют календарную дату в новом поясе. Старую заявку разрешено подтвердить вне нового расписания после смены пояса при соблюдении срока и отсутствии занятости.

## 4. Основные бизнес-процессы

### 4.1. Настройка

Эксперт входит по email-коду, задаёт имя и пояс, настраивает недельные интервалы и исключения, получает личную ссылку. Подключение Яндекса отложено до следующего этапа. Без интеграции вся система работает, но видеоссылка не создаётся.

### 4.2. Подача заявки

Гость открывает личную ссылку без аккаунта, выбирает длительность, дату и доступное время, вводит имя и email, подтверждает email кодом. Тема обязательна (до 120 символов), описание необязательно (до 2000 символов). Поля содержат обычный текст. До отправки заявки гость принимает согласие на обработку персональных данных. Сервер проверяет ограничения и сохраняет ожидающую заявку. Гость получает подтверждение получения и защищённую ссылку на заявку, эксперт — уведомление о новой заявке. Существующие ожидающие заявки не скрывают слот.

### 4.3. Подтверждение

Эксперт рассматривает заявку. При подтверждении сервер повторно проверяет срок и занятость обоих участников. В одной транзакции подтверждает встречу, занимает время обоих, отклоняет пересекающиеся ожидающие заявки с причиной `conflict` и записывает задачи уведомлений и напоминаний. В письме отклонённому гостю есть предложение выбрать другое время по личной ссылке эксперта. Внешняя отправка выполняется после фиксации транзакции. В первом MVP задачи Телемоста не создаются.

Недоступность email не должна откатывать подтверждённую встречу — это принятое техническое правило надёжности ADR-001. На следующем этапе подтверждение не будет зависеть и от доступности Телемоста: при его временном сбое участники получат подтверждение и ICS без ссылки, а ссылка придёт отдельно после успешного повтора.

### 4.4. Отклонение, отзыв, истечение

Организатор может отклонить ожидающую заявку; гость — отозвать свою. Причина необязательна. Об отзыве организатор получает письмо. Необработанная заявка истекает после предельного срока подтверждения. Если команда отклонения или отзыва поступила позже этого срока, заявка считается истёкшей, даже если фоновая задача ещё не обновила запись; ручной переход не выполняется. Закрытая заявка не занимает время и остаётся в истории.

### 4.5. Отмена и перенос

Участники отменяют подтверждённую встречу в пределах TIME-06. Причина необязательна, при наличии видна второй стороне и в уведомлении. Слот освобождается у обоих, но доступен для новых заявок только при выполнении остальных правил, включая минимум 24 часа. Ранее отклонённые заявки автоматически не восстанавливаются.

Перенос реализован отменой и новой заявкой с повторным подтверждением. Сохранение старой встречи на время согласования переноса не предусмотрено.

### 4.6. Изменение расписания

Перед сохранением интервалов или исключений система показывает затронутые будущие встречи и ожидающие заявки, для которых пользователь является организатором. После явного подтверждения встречи вне нового расписания отменяются, заявки отклоняются, участники уведомляются. Без подтверждения изменения не применяются.

Предварительный список имеет версию; если за время просмотра появились изменения в затронутых записях, сохранение требует нового просмотра. Встречи, где владелец расписания является гостем, этим действием не отменяются. Смена часового пояса — отдельная операция по TIME-13.

## 5. Состояния и переходы

Принятая модель состояний первого MVP:

| Состояние | Значение | Допустимые следующие состояния |
| --- | --- | --- |
| pending | Ожидает решения, не занимает слот; другие гости могут запросить то же время | confirmed, rejected, withdrawn, expired |
| confirmed | Подтверждена, занимает время обоих | cancelled; после окончания отображается завершённой |
| rejected | Отклонена вручную, из-за пересечения или изменения расписания | Терминальное |
| withdrawn | Отозвана гостем до подтверждения | Терминальное |
| expired | Истёк срок подтверждения | Терминальное |
| cancelled | Подтверждённая встреча отменена | Терминальное |

Причина перехода хранится отдельно: manual, conflict, schedule_changed, deadline; автор отмены/изменения тоже хранится. «Завершена» означает, что время закончилось, а не доказательство фактического участия.

«Завершена» — вычисляемое отображение `confirmed` после окончания времени, без отдельного перехода состояния. Закрытая или истёкшая заявка не может быть подтверждена.

На следующем этапе состояние видеоссылки будет отдельно от встречи: not_connected, queued, ready, retrying, failed. В первом MVP это состояние не хранится; ошибка будущей интеграции не переводит confirmed обратно в pending.

## 6. Уведомления и ICS

| ID | Событие | Получатели и содержимое |
| --- | --- | --- |
| NOTIFY-01 | Заявка создана | Организатор: новая заявка; гость: заявка получена. |
| NOTIFY-02 | Подтверждение | Участники: детали, время, ICS, ссылка при наличии. |
| NOTIFY-03 | Отклонение или истечение | Гость: новый статус и причина при наличии. |
| NOTIFY-04 | Отмена | Другой участник: детали отмены и причина при наличии. |
| NOTIFY-05 | Закрытие из-за пересечения/расписания | Затронутые участники: статус и системная причина. При конфликте письмо гостю предлагает выбрать другое время и ведёт на страницу эксперта. |
| NOTIFY-06 | Напоминание | Оба участника за 24 часа и за 1 час. Прошедшие к моменту подтверждения напоминания не отправляются задним числом. |
| NOTIFY-07 | Ссылка создана после подтверждения | Отдельное письмо со ссылкой; она появляется в карточке. |
| NOTIFY-08 | Гость отозвал заявку | Организатор: заявка отозвана, причина при наличии. |
| ICS-01 | Экспорт | Скачивание из карточки и вложение при подтверждении. |
| ICS-02 | Ограничение | Обычный импорт файла; нет автоматического обновления или отмены во внешнем календаре. |

Время в письмах показывается в поясе конкретного адресата с указанием пояса; пояс гостя сохраняется с заявкой. Отмена оставшихся напоминаний принята в ADR-001. ADR-001 предусматривает дедупликацию задач и внутренних эффектов. При неопределённом результате SMTP возможен повтор письма; ровно однократная внешняя доставка не гарантируется.

Согласовано: приложение работает только при ручном запуске. После перезапуска неотправленные статусные письма обрабатываются, просроченные напоминания пропускаются, истёкшие заявки закрываются. Задачи сохраняются в SQLite. Напоминания отменённых встреч аннулируются; точная политика обработки — ADR-001.

ICS формируется по RFC 5545: стабильный UID, DTSTAMP, DTSTART/DTEND, SUMMARY, DESCRIPTION, ссылка при наличии; корректное экранирование, переносы строк и UTF-8. Предлагается UTC для дат события. Обновлённый скачиваемый ICS содержит появившуюся ссылку, но ранее импортированное событие сам не изменяет. Это экспорт, а не приглашение с RSVP. [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)

## 7. Реальные внешние интеграции

### 7.1. Яндекс Телемост — следующий этап

Решение ADR-интервью: не реализуется и не проверяется в первом MVP. Описание ниже сохраняет требования будущего этапа; UI подключения, OAuth и фоновые задачи пока не требуются.

Каждый пользователь подключает собственный аккаунт; общий аккаунт сервиса не используется. Интеграция необязательна. При отключённой интеграции не создаются фоновые попытки генерации ссылки. Автогенерация инициируется после подтверждения встречи.

Проверено по официальной документации 30.09.2026: API доступен пользователям Яндекс 360 для бизнеса с аккаунтами на домене организации. Имеющегося обычного аккаунта пользователя недостаточно. Это ограничение интеграции, а не всей системы. [Доступность API](https://yandex.ru/dev/telemost/doc/ru/)

Для авторизации предусмотрен OAuth; создание выполняется POST /v1/telemost-api/conferences с правом telemost-api:conferences.create. В документации описана ошибка ApiRestrictedToOrganizations. [OAuth](https://yandex.ru/dev/telemost/doc/ru/access), [создание встречи](https://yandex.ru/dev/telemost/doc/ru/conference-create)

Решение о покупке тарифа отложено до выяснения стоимости и условий. Стоимость не подтверждена: страница тарифов при проверке не предоставила читаемых данных. Не считать согласованной покупку или наличие подходящего аккаунта.

Предложения реализации: хранить токены только на сервере, шифровать; обрабатывать отзыв доступа отдельно от временных ошибок. При 401/403 не повторять запрос бесконечно, показывать необходимость переподключения. При временных сбоях применять ограниченные повторы с задержкой; прекращать создание после отмены или начала встречи. Точные интервалы и лимит повторов определить в спецификации интеграции. После неопределённого результата запроса не гарантировать отсутствие дубликатов у провайдера без проверки его возможностей идемпотентности.

### 7.2. Email

Коды входа, статусные письма и напоминания отправляются через реального почтового провайдера, в том числе при локальном запуске. Провайдер — Gmail; отправка с аккаунта владельца проекта через SMTP и отдельный пароль приложения. Адрес и секреты задаются локально вне репозитория. Доступность пароля приложения и реальная доставка пока не проверены; условия — ADR-001. Успешная передача провайдеру не равна гарантированной доставке в ящик.

Пользователь отказался от тестового режима с локальным почтовым просмотрщиком и имитацией Телемоста. Ошибки настройки должны отображаться явно; нельзя показывать фиктивный успех. Для реальной сквозной приёмки требуются рабочие учётные данные. Изолированные тесты бизнес-правил не должны отправлять реальные письма.

## 9. Данные и архитектура

Согласованный стек: TypeSpec с генерацией OpenAPI 3.1; TypeScript strict, Node.js 22, Fastify 5, Zod 4; SQLite через better-sqlite3; Vite, React 19 и собственный CSS; Vitest и Playwright; Docker, Docker Compose и GitHub Actions. Один корневой npm workspace и один `package-lock.json` для пакетов `contract`, `server`, `web`, `e2e`. История хранится без автоматического удаления; процедура удаления персональных данных должна быть определена до публичного запуска.

Исходная архитектура [ADR-001](ADR-001.md) обновляется отдельным решением для TypeSpec, Zod, прямого SQL и контейнеризации. Сохраняются модульный монолит, обработчик постоянной очереди внутри процесса, SSE и ручные backup/restore. Публикация приложения начинается после локальной приёмки; образ и CI готовятся в рамках MVP.

Предлагаемые сущности:

`Integration` и `Conference` относятся к следующему этапу и в схему первого MVP не входят.

Для CI выбран GitHub Container Registry. Проверки обычных веток и pull request не публикуют образ; публикация выполняется только по тегу версии при настроенных правах. Создание workflow не разрешает `git push` или фактическую публикацию без отдельного согласия владельца.

Подтверждение и закрытие пересечений атомарны. Необходимо предотвратить конкурирующее подтверждение двух встреч с общим участником, в том числе когда эксперт выступает гостем, а также когда один подтверждённый email гостя встречается у разных экспертов. В SQLite принят BEGIN IMMEDIATE до чтения условий с повторными проверками внутри транзакции. Все операции заявок, занятости и расписания соблюдают общий протокол ADR-001. Блокировки строк PostgreSQL к текущему MVP не относятся.

Внешние вызовы выполняются после фиксации транзакции через надёжную очередь событий (transactional outbox). Повтор HTTP-запроса или фоновой задачи не создаёт вторую внутреннюю встречу. API проверяет права на каждую запись; публичный идентификатор эксперта не даёт доступ к заявкам. Гостевой токен ограничен одной заявкой и хранится только в виде хеша.

## 10. Безопасность и эксплуатационные требования

### 10.1. Уточнённые требования к командам

Следующие правила приняты для первого MVP. Точные маршруты, поля запросов и ответов, коды ошибок, SQL-схема и численные параметры повторов очереди фиксируются в спецификациях модулей до их реализации.

| ID | Требование | Проверяемый результат |
| --- | --- | --- |
| BOOK-01 | Ключ идемпотентности обязателен для команд создания и изменения заявки и расписания. Для гостя область ключа — одно подтверждение email для создания или токен конкретной заявки для дальнейших команд; для эксперта — сессия, действие и объект. Повтор с тем же телом возвращает прежний результат, с другим — конфликт. | Повтор запроса не создаёт вторую заявку или переход; один ключ с иным телом не исполняется. |
| AVAIL-01 | При изменении расписания сервер выдаёт версию и список затронутых записей. Сохранение требует эту версию; изменение списка требует повторного просмотра. | Устаревшее подтверждение последствий не меняет расписание. |

Модель состояний и причин из §5 является контрактом первого MVP. Она не выводится из названий таблиц §9 автоматически.

Следующие требования предложены как техническая основа MVP, а не как согласованные численные SLA:

- Проверка входных данных на сервере; безопасное отображение обычного текста; отсутствие токенов, кодов входа и содержимого писем в логах.
- Одноразовые коды ограничены по сроку и попыткам согласно AUTH-08, хранятся в виде хеша; отправка ограничивается по email/IP согласно AUTH-12.
- Защищённые сессии эксперта, HttpOnly-cookie, защита от CSRF при cookie-auth, HTTPS на публичном сервере. Сроки сессии и гостевой ссылки заданы в AUTH-09/10; гостевые коды используются однократно, ссылки ограничены доступом к одной заявке. OAuth относится к следующему этапу.
- Секреты вне репозитория; пример переменных окружения без значений; конфигурация локального и серверного запуска.
- Миграции БД, журнал ошибок фоновых задач и интеграций, документированное восстановление после перезапуска.
- При разрыве канала обновлений клиент сообщает об этом и повторно запрашивает актуальные данные после восстановления.
- История не удаляется автоматически; процедуры удаления аккаунта и персональных данных не определены и требуют решения до реальной публичной эксплуатации.
- Контейнер хранит SQLite в постоянном томе; секреты задаются вне образа. CI выполняет сборку и тесты, а публикацию образа в реестр — только при разрешённом событии и наличии настроенных прав. Наличие workflow не означает выполненный деплой.

## 12. План реализации по SDD

Для каждой возможности: спецификация сценариев и инвариантов → контракт API/данных → план реализации → код → проверки с привязкой к AC. Каркас репозитория может предшествовать детальным контрактам модулей, но не реализации их поведения. Изменения требований сначала отражаются в этом документе; архитектурные решения — в отдельных ADR.

Согласованная карта возможностей и порядок: `identity` (эксперт и гостевая проверка email), `privacy` (согласия и cookie) → `availability` (расписание и слоты) → `bookings` (заявки и конфликты) → `notifications` (письма и ICS) и `web` (публичная страница и кабинет) → `operations` (контейнер, проверки и CI). Контракты каждого модуля фиксируются до его кода. Модули используют только явно заданные интерфейсы предыдущих модулей; детали таблиц не становятся публичным API. Сценарии и документальный контракт первого модуля — [спецификация identity](specs/identity.md).

Целевая структура репозитория: `docs/pdr/0001-*.md` для продуктового решения, `docs/adr/0001-*.md` и последующие файлы для архитектурных решений, `contract/main.tsp` и сгенерированный `contract/openapi.yaml`, `server/src/` с SQL в `server/src/repository.ts`, `web/src/`, `server/tests/`, по возможности `e2e/`, корневой `AGENTS.md`, `README.md`, `Dockerfile`, `docker-compose.yml` и один корневой `package-lock.json`. При переносе нынешних документов обновить ссылки без создания параллельных источников требований.

Планируемые команды после появления конфигурации: `npm install`, `npm run build`, `npm test`, `npm run lint`, `docker compose up --build`. Пока приложения и скриптов нет, команды не проверены. README должен содержать только реально проверенный порядок запуска. Стиль кода: TypeScript strict, 2 пробела, `camelCase` для функций и переменных, `PascalCase` для типов и компонентов; пользовательские тексты на русском. Проверки: Vitest для расчёта времени и правил, Fastify inject и временная SQLite для API и конкуренции, Playwright для сквозного пути эксперта и гостя. Перед кодом каждого модуля нужны сценарии, контракты и согласование с владельцем проекта. Добавление новых зависимостей вне выбранного стека, изменение границ и архитектуры, удаление данных и публикация требуют отдельного согласования. Код MVP начинается только после отдельного согласия владельца.

Definition of Done MVP: требования реализованной области трассируются на проверки, ключевые сценарии проходят, контейнерный локальный запуск воспроизводим по README, настройки и ручные backup/restore описаны, секретов в репозитории нет, известные ограничения перечислены. ## 14. Источники и порядок изменений

Бизнес-требования: последовательное интервью с владельцем продукта в этом чате. Решения от 05.10.2026 заменяют противоречащие им ранние: гость без аккаунта подтверждает email кодом, pending не занимает слот, эксперт выбирает одну заявку; стек и целевая структура заданы изображениями. Яндекс необязателен; занятость подтверждённых встреч учитывается у обоих участников. Карта работ согласована; код MVP требует отдельного разрешения.

Референсы для ясного изложения: [условия Яндекс Афиши](https://yandex.ru/legal/afisha_termsofuse/ru/) и [политика cookie Яндекса](https://yandex.ru/legal/cookies_policy/ru/). Их текст и сведения об операторе не переносятся в документы MyBooking. Решение владельца от 05.10.2026: для учебного MVP достаточно кратких собственных пояснений, юридическая подготовка к публичному запуску отложена.

Официальные технические источники, проверены 30.09.2026:

- [API Телемоста: ограничения](https://yandex.ru/dev/telemost/doc/ru/).
- [API Телемоста: OAuth](https://yandex.ru/dev/telemost/doc/ru/access).
- [API Телемоста: создание встречи](https://yandex.ru/dev/telemost/doc/ru/conference-create).

- [RFC 5545: iCalendar](https://www.rfc-editor.org/rfc/rfc5545).

Изменения v1.1: по ADR-интервью PostgreSQL заменён на SQLite, запуск ограничен локальным, выбран Gmail, Телемост и удаление аккаунта отложены, согласованы backup/restore и правила времени. [ADR-001](ADR-001.md) содержит технические решения и их последствия.

Изменения v1.2: по уточнениям владельца продукта закреплены истечение заявки перед поздними командами отклонения/отзыва, отсутствие автоматического восстановления отклонённых заявок, письмо организатору об отзыве и показ времени в письме в поясе адресата. Уточнена атомарная запись фоновых задач; владелец подтвердил наличие средств для проверки Gmail, но отправка ещё не проверена.

Изменения v1.4: владелец согласовал сроки и лимиты входа, нормализацию email, область идемпотентности гостя, состояния, версию последствий расписания, ручной запрос удаления данных, отсутствие необязательных cookie и публикацию в GHCR по тегу версии. Телемост исключён из схемы и приёмки первого MVP.

Изменения v1.5: согласованы порядок первого входа эксперта, срок и область гостевого подтверждения email, восстановление гостевой ссылки без раскрытия заявки и момент отзыва старого токена.

Дополнение v1.5: согласован документальный HTTP-контракт `identity`, включая погашение гостевого подтверждения после успешной заявки, токен гостевой ссылки во фрагменте URL и нейтральный ответ восстановления без утверждения доставки письма.

При изменении требования сохранять его ID, обновлять связанные критерии приёмки и отмечать причину. Новые технические решения не считать автоматически согласованными бизнес-требованиями.
