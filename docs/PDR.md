# MyBooking — PDR: требования к продукту

Версия: 1.2. Дата: 04.10.2026. Формат: документ требований к продукту для Specification-Driven Development (SDD).

Статус: результаты продуктового и архитектурного интервью зафиксированы; см. [ADR-001](ADR-001.md). Технические предложения и открытые вопросы явно отделены от согласованных требований. Документ не означает, что приложение уже реализовано или интеграции проверены вживую.

## 1. Цель и границы продукта

MyBooking — учебный веб-MVP для бронирования индивидуальных созвонов с ручным подтверждением. Пользователь делится личной ссылкой, получает заявки, подтверждает удобную встречу и отправляет участникам сведения о ней.

Каждый зарегистрированный пользователь одновременно может быть организатором и гостем. Роль определяется конкретной встречей. Это окончательное решение заменяет первоначальный вариант с единственным организатором.

Ценность: согласование времени без переписки, отсутствие двойного бронирования, единое расписание, email-уведомления, ICS и необязательная интеграция с Телемостом.

Успех MVP: два пользователя проходят реальный путь от входа по email до подтверждения и отмены встречи; пересечения предотвращаются; письма доставляются через реальный сервис; ICS импортируется; Телемост отложен на следующий этап и не входит в приёмку первого MVP.

Не входят: оплата, каталог пользователей, команды и распределение заявок, групповые встречи, синхронизация внешних календарей, полноценные календарные приглашения и их обновления, ручной ввод ссылки, мультиязычность, имитация внешних интеграций в локальном приложении. Промышленный SLA не установлен.

## 2. Пользователи и доступ

| ID | Согласованное требование |

## 3. Правила времени и доступности

| ID | Правило |
| --- | --- |
| TIME-01 | Еженедельное расписание, несколько интервалов на каждый день недели. Отдельные даты можно полностью исключить. |
| TIME-02 | Длительность на выбор гостя: 15, 30 или 60 минут. Шаг начала — 15 минут. |
| TIME-03 | Встреча целиком помещается в интервал доступности организатора. Перерыв между встречами не требуется. |
| TIME-04 | Заявка подаётся минимум за 24 часа до начала. Горизонт бронирования — 30 дней. |
| TIME-05 | Подтверждение допускается не позднее чем за 3 часа до начала; необработанная заявка затем истекает. |
| TIME-06 | Гость отменяет встречу не позднее чем за 3 часа до начала. Организатор — в любой момент до начала. |
| TIME-07 | Подтверждённые встречи блокируют время обоих участников независимо от их роли. |
| TIME-08 | Занятый у любого участника слот нельзя выбрать или забронировать. Проверка повторяется на сервере при подаче и подтверждении. |
| TIME-09 | Ожидающие заявки не занимают время. Их количество и число будущих подтверждённых встреч не ограничены. |
| TIME-10 | При подтверждении закрываются все пересекающиеся ожидающие заявки обоих участников, затронутые пользователи уведомляются. |
| TIME-11 | Эти параметры общие для всех; организатор не изменяет длительности, шаг, горизонт и сроки. |
| TIME-12 | Расписание задаётся в часовом поясе владельца; время для посетителя отображается в поясе его профиля. |
| TIME-13 | Смена пояса сохраняет часы еженедельного расписания, но не фактическое время уже созданных заявок и встреч и ничего автоматически не отменяет. |

Точная семантика времени (границы, DST и смена пояса согласованы в ADR-интервью; способы хранения закреплены в ADR-001):

- Время хранится как UTC-момент, пояс — IANA-идентификатор. Серверное время авторитетно.
- Интервалы полуоткрытые: [начало, конец). Встречи 10:00–10:30 и 10:30–11:00 не пересекаются.
- Нижняя граница подачи включительна: start >= now + 24 часа. Верхняя: start <= now + 30 суток. Горизонт означает ровно 30 × 24 часа и ограничивает начало встречи.
- Ровно за 3 часа подтверждение и отмена гостем разрешены; при меньшем остатке — запрещены. Истечение определяется этой проверкой, даже если фоновая задача ещё не обработала запись.
- Начала выравниваются на :00, :15, :30, :45 по времени организатора. Невалидные интервалы расписания отклоняются.
- Свобода гостя определяется его подтверждёнными встречами; собственные часы приёма заявок гостя не ограничивают его участие у другого организатора.
- Несуществующее локальное время при DST пропускается; повторяющийся час даёт два варианта с разными UTC-моментами и явным смещением. Длительность считается в фактических минутах; вся встреча должна попадать в доступность.
- Интервалы через полночь задаются двумя частями; 24:00 допустимо как конец дня. TIME-03 сохраняется: встреча помещается в одну часть.
- При смене пояса исключённые даты сохраняют календарную дату в новом поясе. Старую заявку разрешено подтвердить вне нового расписания после смены пояса при соблюдении срока и отсутствии занятости.

## 4. Основные бизнес-процессы

### 4.1. Настройка

Пользователь входит по email-коду, задаёт имя и пояс, настраивает недельные интервалы и исключения, получает личную ссылку. Подключение Яндекса отложено до следующего этапа. Без интеграции вся система работает, но видеоссылка не создаётся.

### 4.2. Подача заявки

Гость открывает ссылку, входит, выбирает длительность, дату и свободное у обоих время. Имя берётся из профиля; тема обязательна (до 120 символов), описание необязательно (до 2000 символов). Поля содержат обычный текст. Сервер проверяет ограничения и сохраняет ожидающую заявку. Гость получает подтверждение получения, организатор — уведомление о новой заявке.

### 4.3. Подтверждение

Организатор рассматривает заявку. При подтверждении сервер повторно проверяет срок и занятость обоих участников. В одной транзакции подтверждает встречу, занимает время обоих, закрывает пересекающиеся ожидающие заявки и записывает задачи уведомлений и напоминаний. Внешняя отправка выполняется после фиксации транзакции. В первом MVP задачи Телемоста не создаются.

Недоступность email не должна откатывать подтверждённую встречу — это принятое техническое правило надёжности ADR-001. На следующем этапе подтверждение не будет зависеть и от доступности Телемоста: при его временном сбое участники получат подтверждение и ICS без ссылки, а ссылка придёт отдельно после успешного повтора.

### 4.4. Отклонение, отзыв, истечение

Организатор может отклонить ожидающую заявку; гость — отозвать свою. Причина необязательна. Об отзыве организатор получает письмо. Необработанная заявка истекает после предельного срока подтверждения. Если команда отклонения или отзыва поступила позже этого срока, заявка считается истёкшей, даже если фоновая задача ещё не обновила запись; ручной переход не выполняется. Закрытая заявка не занимает время и остаётся в истории.

### 4.5. Отмена и перенос

Участники отменяют подтверждённую встречу в пределах TIME-06. Причина необязательна, при наличии видна второй стороне и в уведомлении. Слот освобождается у обоих, но доступен для новых заявок только при выполнении остальных правил, включая минимум 24 часа. Ранее отклонённые заявки автоматически не восстанавливаются.

Перенос реализован отменой и новой заявкой с повторным подтверждением. Сохранение старой встречи на время согласования переноса не предусмотрено.

### 4.6. Изменение расписания

Перед сохранением интервалов или исключений система показывает затронутые будущие встречи и ожидающие заявки, для которых пользователь является организатором. После явного подтверждения встречи вне нового расписания отменяются, заявки отклоняются, участники уведомляются. Без подтверждения изменения не применяются.

Предложение: предварительный список имеет версию; если за время просмотра появились изменения, сохранение требует нового просмотра. Встречи, где владелец расписания является гостем, этим действием не отменяются. Смена часового пояса — отдельная операция по TIME-13.

## 5. Состояния и переходы

Предлагаемая модель, соответствующая согласованному процессу:

| Состояние | Значение | Допустимые следующие состояния |
| --- | --- | --- |
| pending | Ожидает решения, не занимает слот | confirmed, rejected, withdrawn, expired |
| confirmed | Подтверждена, занимает время обоих | cancelled; после окончания отображается завершённой |
| rejected | Отклонена вручную, из-за пересечения или изменения расписания | Терминальное |
| withdrawn | Отозвана гостем до подтверждения | Терминальное |
| expired | Истёк срок подтверждения | Терминальное |
| cancelled | Подтверждённая встреча отменена | Терминальное |

Причина перехода хранится отдельно: manual, conflict, schedule_changed, deadline; автор отмены/изменения тоже хранится. «Завершена» означает, что время закончилось, а не доказательство фактического участия.

Состояние видеоссылки отдельно от встречи: not_connected, queued, ready, retrying, failed. Ошибка интеграции не переводит confirmed обратно в pending.

## 6. Уведомления и ICS

| ID | Событие | Получатели и содержимое |
| --- | --- | --- |
| NOTIFY-01 | Заявка создана | Организатор: новая заявка; гость: заявка получена. |
| NOTIFY-02 | Подтверждение | Участники: детали, время, ICS, ссылка при наличии. |
| NOTIFY-03 | Отклонение или истечение | Гость: новый статус и причина при наличии. |
| NOTIFY-04 | Отмена | Другой участник: детали отмены и причина при наличии. |
| NOTIFY-05 | Закрытие из-за пересечения/расписания | Затронутые участники: статус и системная причина. |
| NOTIFY-06 | Напоминание | Оба участника за 24 часа и за 1 час. Прошедшие к моменту подтверждения напоминания не отправляются задним числом. |
| NOTIFY-07 | Ссылка создана после подтверждения | Отдельное письмо со ссылкой; она появляется в карточке. |
| NOTIFY-08 | Гость отозвал заявку | Организатор: заявка отозвана, причина при наличии. |
| ICS-01 | Экспорт | Скачивание из карточки и вложение при подтверждении. |
| ICS-02 | Ограничение | Обычный импорт файла; нет автоматического обновления или отмены во внешнем календаре. |

Время в письмах показывается в поясе конкретного адресата с указанием пояса. Отмена оставшихся напоминаний принята в ADR-001. ADR-001 предусматривает дедупликацию задач и внутренних эффектов. При неопределённом результате SMTP возможен повтор письма; ровно однократная внешняя доставка не гарантируется.

Согласовано: приложение работает только при ручном запуске. После перезапуска неотправленные статусные письма обрабатываются, просроченные напоминания пропускаются, истёкшие заявки закрываются. Задачи сохраняются в SQLite. Напоминания отменённых встреч аннулируются; точная политика обработки — ADR-001.

ICS формируется по RFC 5545: стабильный UID, DTSTAMP, DTSTART/DTEND, SUMMARY, DESCRIPTION, ссылка при наличии; корректное экранирование, переносы строк и UTF-8. Предлагается UTC для дат события. Обновлённый скачиваемый ICS содержит появившуюся ссылку, но ранее импортированное событие сам не изменяет. Это экспорт, а не приглашение с RSVP. [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)

## 7. Реальные внешние интеграции

### 7.1. Яндекс Телемост — следующий этап

Решение ADR-интервью: не реализуется и не проверяется в первом MVP. Описание ниже сохраняет требования будущего этапа; UI подключения, OAuth и фоновые задачи пока не требуются.

Каждый пользователь подключает собственный аккаунт; общий аккаунт сервиса не используется. Интеграция необязательна. При отключённой интеграции не создаются фоновые попытки генерации ссылки. Автогенерация инициируется после подтверждения встречи.

Проверено по официальной документации 30.09.2026: API доступен пользователям Яндекс 360 для бизнеса с аккаунтами на домене организации. Имеющегося обычного аккаунта пользователя недостаточно. Это ограничение интеграции, а не всей системы. [Доступность API](https://yandex.ru/dev/telemost/doc/ru/)

Для авторизации предусмотрен OAuth; создание выполняется POST /v1/telemost-api/conferences с правом telemost-api:conferences.create. В документации описана ошибка ApiRestrictedToOrganizations. [OAuth](https://yandex.ru/dev/telemost/doc/ru/access), [создание встречи](https://yandex.ru/dev/telemost/doc/ru/conference-create)

Решение о покупке тарифа отложено до выяснения стоимости и условий. Стоимость не подтверждена: страница тарифов при проверке не предоставила читаемых данных. Не считать согласованной покупку или наличие подходящего аккаунта.

Предложения реализации: хранить токены только на сервере, шифровать; обрабатывать отзыв доступа отдельно от временных ошибок. При 401/403 не повторять запрос бесконечно, показывать необходимость переподключения. При временных сбоях применять ограниченные повторы с задержкой; прекращать создание после отмены или начала встречи. Точные интервалы и лимит повторов определить в спецификации интеграции. После неопределённого результата запроса не гарантировать отсутствие дубликатов у провайдера без проверки его возможностей идемпотентности.

### 7.2. Email

Коды входа, статусные письма и напоминания отправляются через реального почтового провайдера, в том числе при локальном запуске. Провайдер — Gmail; отправка с аккаунта владельца проекта через SMTP и отдельный пароль приложения. Адрес и секреты задаются локально вне репозитория. Доступность пароля приложения и реальная доставка пока не проверены; условия — ADR-001. Успешная передача провайдеру не равна гарантированной доставке в ящик.

Пользователь отказался от тестового режима с локальным почтовым просмотрщиком и имитацией Телемоста. Ошибки настройки должны отображаться явно; нельзя показывать фиктивный успех. Для реальной сквозной приёмки требуются рабочие учётные данные. Изолированные тесты бизнес-правил не должны отправлять реальные письма.

При получении обновления выбранный ставший недоступным слот сбрасывается с объяснением. На мобильном недельная сетка должна оставаться управляемой без потери функций.

## 9. Данные и архитектура

Согласованный стек: React + TypeScript; Node.js + TypeScript; SQLite. Только ручной локальный запуск на одном компьютере для нескольких знакомых, в том числе в разных браузерах/профилях. Приоритет — быстрый MVP с возможностью развития. Публичный сервер и PostgreSQL — возможный будущий этап, сейчас не реализуются. История хранится без автоматического удаления; самостоятельное удаление аккаунта отложено до публичного запуска.

Принятая архитектура [ADR-001](ADR-001.md): модульный монолит, Fastify, React/Vite, SQLite через Drizzle и better-sqlite3, обработчик постоянной очереди внутри процесса и SSE. Ручные backup/restore входят в MVP. Библиотеки выбраны автором ADR по поручению пользователя.

| Сущность | Основные данные |
| --- | --- |
| User | id, email, name, timezone, publicId, theme |
| LoginChallenge / Session | Хеш кода, срок, число попыток / сессия, срок, отзыв |
| AvailabilityInterval | userId, weekday, localStart, localEnd |
| ExcludedDate | userId, localDate |
| Booking | id, organizerId, guestId, startUtc, endUtc, subject, description, status, reason, version |
| BookingTransition | bookingId, старый/новый статус, actorId, причина, timestamp |
| Integration | userId, provider, защищённые токены, состояние |
| Conference | bookingId, providerId, joinUrl, состояние, попытки |
| Outbox / Job | Тип события, bookingId, адресат, scheduledAt, состояние, ключ дедупликации |

Подтверждение и закрытие пересечений атомарны. Необходимо предотвратить конкурирующее подтверждение двух встреч с общим участником, в том числе когда его роли различаются. В SQLite принят BEGIN IMMEDIATE до чтения условий с повторными проверками внутри транзакции. Все операции заявок, занятости и расписания соблюдают общий протокол ADR-001. Блокировки строк PostgreSQL к текущему MVP не относятся.

Внешние вызовы выполняются после фиксации транзакции через надёжную очередь событий (transactional outbox). Повтор HTTP-запроса или фоновой задачи не создаёт вторую внутреннюю встречу. API проверяет права на каждую запись; случайный publicId не заменяет авторизацию.

## 10. Безопасность и эксплуатационные требования

Следующие требования предложены как техническая основа MVP, а не как согласованные численные SLA:

- Проверка входных данных на сервере; безопасное отображение обычного текста; отсутствие токенов, кодов входа и содержимого писем в логах.
- Одноразовые коды ограничены по сроку и попыткам, хранятся в виде хеша; отправка ограничивается по email/IP. Конкретные значения закрепляются в auth-спецификации.
- Защищённые сессии, HttpOnly-cookie, защита от CSRF при cookie-auth, HTTPS на публичном сервере, OAuth state и проверка callback.
- Секреты вне репозитория; пример переменных окружения без значений; конфигурация локального и серверного запуска.
- Миграции БД, журнал ошибок фоновых задач и интеграций, документированное восстановление после перезапуска.
- При разрыве канала обновлений клиент сообщает об этом и повторно запрашивает актуальные данные после восстановления.
- История не удаляется автоматически; процедуры удаления аккаунта и персональных данных не определены и требуют решения до реальной публичной эксплуатации.

## 11. Критерии приёмки и трассировка

| ID | Требования | Проверяемый сценарий |
| --- | --- | --- |
| AC-01 | AUTH-01/02/04 | Без входа календарь недоступен. Верный одноразовый код открывает профиль; использованный код повторно не принимается. |
| AC-02 | AUTH-03/05/06 | Два пользователя имеют разные ссылки; каждый может принимать и подавать заявки; третий не читает чужую заявку через API. |
| AC-03 | TIME-01/02/03 | Для интервалов 09:00–12:00 и 14:00–18:00 нет слотов через перерыв; длительности 15/30/60 и шаг 15 соблюдены. |
| AC-04 | TIME-04 | До начала менее 24 часов — отказ; ровно 24 часа — разрешение. Проверены обе границы горизонта по утверждённой семантике. |
| AC-05 | TIME-05 | Подтверждение ровно за 3 часа разрешено, позже запрещено; ожидающая заявка истекает и уведомляет гостя. |
| AC-06 | TIME-07/08 | Подтверждённая встреча гостя у другого организатора исключает пересекающиеся слоты; прямой запрос API тоже отклоняется. |
| AC-07 | TIME-09/10 | Несколько pending на одно время допустимы. Подтверждение одной закрывает пересекающиеся pending обоих участников и уведомляет их контрагентов. |
| AC-08 | TIME-07/08 | Два одновременных подтверждения с общим участником: успешна не более одной пересекающейся встречи; соседние разрешены. |
| AC-09 | TIME-06 | Гость не отменяет за 2 часа, организатор отменяет; новая заявка после отмены всё равно требует минимум 24 часа. |
| AC-10 | Раздел 4.6 | Изменение расписания показывает затронутые записи; отказ сохраняет старое расписание; согласие отменяет/отклоняет и уведомляет. |
| AC-11 | TIME-12/13 | Смена пояса меняет отображение, сохраняет UTC существующих встреч и часы недельного расписания, не отменяет записи. |
| AC-12 | Раздел 4.2 | Пустая тема и тема длиннее 120 символов отклоняются; описание до 2000 принимается, длиннее — нет; текст не исполняется как HTML. |
| AC-13 | NOTIFY-01–08 | Реальные письма приходят нужным адресатам, в том числе уведомление организатору об отзыве; время показано в поясе получателя; отменённая встреча не получает напоминания; пропущенное суточное напоминание не отправляется задним числом. |
| AC-14 | Раздел 7.1 | Без Яндекса подтверждение и ICS работают без ссылки и без попыток её создания. |
| AC-15 (следующий этап) | Раздел 7.1 | С подходящим реальным аккаунтом создаётся ссылка; временная ошибка не отменяет встречу; после успеха ссылка приходит отдельно. Заблокировано для проверки до получения доступа. |
| AC-16 | ICS-01/02 | ICS импортируется с правильными датой, длительностью и русским текстом; при наличии содержит ссылку; обновление внешнего календаря не обещается. |
| AC-17 | UI-01–09 | На телефоне и компьютере работают оба вида календаря, обе темы, основные действия; изменения видны во второй сессии без перезагрузки. |
| AC-18 | Раздел 9 | Перезапуск обработчика не теряет зафиксированное событие; повтор обработки не создаёт повторную внутреннюю встречу. |
| AC-19 | Раздел 9, ADR-001 | Ручная резервная копия восстанавливается при остановленном приложении; целостность и схема проверены, очередь возобновляется явно. |

Приёмка включает тесты чистой логики времени, интеграционные тесты SQLite и конкурентных операций, проверки разграничения доступа и ручной сквозной сценарий с реальными интеграциями. Недоступную интеграцию отмечать как непроверенную, не заменять вымышленным успехом.

## 12. План реализации по SDD

Для каждой возможности: спецификация сценариев и инвариантов → контракт API/данных → план реализации → код → проверки с привязкой к AC. Изменения требований сначала отражаются в этом документе; архитектурные решения — в отдельных ADR.

| Этап | Содержание | Выход |
| --- | --- | --- |
| 0 | Уточнить открытые решения, настроить выбранный Gmail SMTP, зафиксировать перенос Яндекс API на следующий этап | Спецификации интеграций и список доступных проверок |
| 1 | Вход, профиль, личная ссылка, права доступа | AUTH и AC-01/02 |
| 2 | Расписание, исключения, пояса, расчёт доступности | TIME и AC-03/04/06/11 |
| 3 | Подача, подтверждение, конфликты, отмена, изменение расписания | Автомат состояний и AC-05/07–10/12 |
| 4 | Фоновые события, реальные письма, ICS; Телемост отдельным следующим этапом | AC-13/14/16/18 |
| 5 | Адаптивный календарь, две темы, обновления, документация запуска | AC-17 и сквозная приёмка |

Definition of Done MVP: требования реализованной области трассируются на проверки, ключевые сценарии проходят, локальный запуск воспроизводим по инструкции, локальные настройки и ручные backup/restore описаны, секретов в репозитории нет, известные ограничения перечислены. Интеграцию Телемоста нельзя объявлять проверенной без реального доступного аккаунта.
