# ADR-002 — Гость без аккаунта, контракт API и контейнер MVP

Дата: 05.10.2026. Статус: согласовано как целевая архитектура; каркас создан в ветке задачи 001, модули ещё не реализованы.

Основание: решения владельца проекта от 05.10.2026 и [PDR v1.6](PDR.md). Этот ADR заменяет противоречащие ему части [ADR-001](ADR-001.md), сохраняя его транзакционный протокол, очередь, правила времени, SMTP, SSE и backup/restore.

## Контекст

Первоначальная модель требовала аккаунт для обоих участников, Drizzle и локальный запуск процесса. Новое решение требует публичной страницы эксперта для гостя без аккаунта, TypeSpec/OpenAPI 3.1, Zod 4, SQL через better-sqlite3, контейнер и базовый CI. Ожидающие заявки не занимают слот; эксперт выбирает одну, остальные пересекающиеся заявки отклоняются.

## Решение

### Идентичность и право доступа

Эксперт имеет аккаунт и входит по одноразовому email-коду. Аккаунт создаётся после успешной проверки кода; до заполнения имени и IANA-пояса доступны только профиль и выход. Гость не имеет аккаунта и открывает свободные слоты без входа. Перед подачей заявки он подтверждает свой email одноразовым кодом; доказательство действует 10 минут, однократно и для выбранного эксперта. Заявка хранит подтверждённый нормализованный email, имя и выбранный часовой пояс гостя. Если email принадлежит эксперту, для проверки занятости используется та же личность независимо от роли. Угаданный адрес не даёт права читать чужие заявки.

После подачи гость получает ссылку на конкретную заявку с непрозрачным токеном во фрагменте URL; API принимает токен через заголовок, не через путь или query. Сервер хранит хеш токена; ссылка даёт только права гостя на эту заявку. Срок ссылки — 30 дней. Восстановление по ID заявки требует проверки кода на сохранённый email; внешний ответ не раскрывает наличие заявки. Запрос восстановления не отзывает действующую ссылку, успешная проверка отзывает её и выдаёт новую. Публичный идентификатор эксперта даёт доступ только к опубликованной доступности.

Согласие на обработку данных проверяется сервером перед запросом email-кода эксперта и гостя и связывается с созданным аккаунтом или заявкой. Версия текста и время принятия сохраняются. Необходимые cookie используются для сессии эксперта и защиты действий; в первом MVP необязательных cookie нет, уведомление только информационное. Для учебного MVP достаточно краткого собственного пояснения; юридическая подготовка к публичному запуску выполняется отдельно.

### Контракт и хранилище

`contract/main.tsp` — источник публичного API. Генерация создаёт `contract/openapi.yaml` формата OpenAPI 3.1; в CI проверяется, что генерация воспроизводима. Fastify 5 проверяет входные данные через Zod 4. Контракт не экспортирует схему SQLite, секреты и внутреннюю очередь.

Сервер использует TypeScript strict и Node.js 24.21.0 LTS. Корневой workspace фиксирует npm 12.2.0, совместимые версии пакетов и один lockfile. Выбор TypeScript 6.0.3 вместо опубликованного 7.0.2 обусловлен ограничением `typescript-eslint`; точные версии и источники приведены в [исследовании](research/toolchain-versions.md). SQL хранится в `server/src/repository.ts` согласно целевой структуре. Миграции схемы должны быть явными и воспроизводимыми. Drizzle и Drizzle Kit из ADR-001 исключаются; бизнес-правила остаются вне SQL и HTTP. Непосредственный SQL не меняет требования `BEGIN IMMEDIATE`, коротких синхронных транзакций и атомарной записи переходов и задач.

Подтверждённую встречу нельзя пересечь с другой подтверждённой встречей того же эксперта или подтверждённого email гостя. Несколько `pending` на один интервал допустимы. При подтверждении одной заявки в одной транзакции отклоняются все пересекающиеся `pending`, затрагивающие любого из двух участников; письма гостям предлагают выбрать другое время. Внешние вызовы выполняются после commit.

### Пакеты, контейнер и CI

Корневой npm workspace содержит четыре пакета: `contract`, `server`, `web`, `e2e`; один корневой `package-lock.json`. React 19 и Vite собирают интерфейс с собственным CSS. Vitest проверяет модульные, интеграционные и контрактные сценарии; Playwright — сквозные. Корневые `Dockerfile` и `docker-compose.yml` запускают собранный сервер и интерфейс одной командой; SQLite хранится в постоянном томе, секреты передаются через окружение и не входят в образ.

GitHub Actions выполняет сборку и тесты. Публикация образа в GHCR настроена только для тега версии при наличии прав. Создание конфигурации CI не означает разрешения выполнить публикацию, `git push` или деплой. Сам деплой — этап после локальной реализации и приёмки MVP.

## Последствия и проверка

Гостю не нужна учётная запись, но проверка email добавляет шаг перед заявкой. Занятость гостя сопоставляется между экспертами по подтверждённому email с нормализацией по PDR AUTH-11. Защищённые ссылки требуют защиты от утечек через логи и ограничения доступа к одной записи. Контракт и SQL перестают иметь общий генератор типов, поэтому нужны контрактные проверки. Контейнерный запуск требует постоянного тома и отдельного порядка backup/restore.

Проверки привязаны к AC-01/02/06–08/20–23 PDR: вход эксперта, гостевой код без аккаунта, изоляция ссылок, конкурирующие подтверждения, согласие, воспроизводимая генерация контракта, сборка и локальный запуск контейнера. Реальная доставка Gmail, публикация образа и деплой считаются непроверенными до фактического выполнения.
