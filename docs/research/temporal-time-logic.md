# Temporal для чистой логики времени задачи 007

Проверено 5 октября 2026 года. Исследование касается выбранного `@js-temporal/polyfill`, а не меняет PDR или внутренний контракт задачи.

## Версия и среда

- На [странице пакета npm](https://www.npmjs.com/package/@js-temporal/polyfill) и в [списке релизов разработчиков](https://github.com/js-temporal/temporal-polyfill/releases) последняя опубликованная версия — **0.5.1**. В [манифесте тега v0.5.1](https://github.com/js-temporal/temporal-polyfill/blob/v0.5.1/package.json) заявлено `engines.node: >=12`; README на npm указывает поддержку Node.js 14+. Оба условия допускают выбранный Node.js 24.21.0. Это проверка заявленной совместимости, не результат установки и запуска.
- В [списке изменений 0.5.0](https://github.com/js-temporal/temporal-polyfill/blob/v0.5.1/CHANGELOG.md) зафиксировано удаление `Temporal.TimeZone`. В [декларациях типов v0.5.1](https://github.com/js-temporal/temporal-polyfill/blob/v0.5.1/index.d.ts) нет `getPossibleInstantsFor()`. Примеры с этим методом относятся к старому API и для 0.5.1 не подходят.

## Локальное время и DST

- [Документация Temporal о неоднозначности времени](https://tc39.es/proposal-temporal/docs/timezone.html) и [описание `ZonedDateTime.from`](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) определяют `disambiguation: 'earlier' | 'later' | 'reject'`. При повторении часа первые два варианта дают разные UTC-моменты для одного локального времени. При пропуске часа они дают сдвинутые локальные значения; режим по умолчанию `compatible` тоже может сдвинуть несуществующее время.
- Вывод для `possibleInstants`: строго разобрать локальную дату и время, построить два `ZonedDateTime.from` с `earlier` и `later` **без входного смещения**, затем для каждого сравнить возвращённые локальные дату и время с исходными. Несовпадающие варианты отбросить, одинаковые UTC-моменты дедуплицировать, остальные отсортировать по `epochMilliseconds`. Это даёт пустой результат для DST gap, два момента для overlap и один для обычного времени. Такой алгоритм — вывод из поведения документированных режимов; его нужно подтвердить Vitest на датах `Europe/Berlin` из карточки 007. `reject` сам по себе не позволяет отличить gap от overlap, так как оба вызывают `RangeError`.
- [Документация `ZonedDateTime`](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) предупреждает, что календарные дни на переходах могут длиться 23 или 25 фактических часов. Границы 24 часа, 3 часа и 30 × 24 часа из PDR/ADR следует вычислять в UTC epoch milliseconds, а конец встречи — прибавлением фактических минут.

## Пояс и формат ответа

- [Документация Temporal](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) принимает IANA Zone/Link ID, а также фиксированные смещения вроде `+05:30`. Поэтому успешный вызов Temporal сам по себе **не доказывает**, что вход — IANA ID. Практическая проверка: отвергнуть пустую строку, пробелы по краям, строки со знаком `+`/`-` в начале и аннотации `[...]`, затем передать оставшийся ID в `new Intl.DateTimeFormat('en', { timeZone: id })` и обработать `RangeError`. [ECMA-402](https://tc39.es/ecma402/#sec-use-of-the-iana-time-zone-database) определяет именованные Zone/Link ID; [документация параметра `timeZone`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat/DateTimeFormat#timezone) подтверждает, что Intl также принимает смещения, поэтому начальный знак нужно исключать отдельно. `UTC` и IANA Link ID допустимы. `Intl.supportedValuesOf('timeZone')` не годится как полный валидатор: [Temporal](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) указывает, что список содержит только канонические ID и исключает часть допустимых Link ID.
- `Temporal.Instant.fromEpochMilliseconds(ms).toZonedDateTimeISO(timeZone)` преобразует существующий момент в локальное представление; [свойство `offset`](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) возвращает явное смещение. `toString({ timeZoneName: 'never', calendarName: 'never', fractionalSecondDigits: 3 })` по [документации сериализации](https://tc39.es/proposal-temporal/docs/zoneddatetime.html) выводит ISO-совместимую строку со смещением без аннотации `[IANA]`. Смена пояса у того же `Instant` меняет локальную строку, но сохраняет `epochMilliseconds`.

## Фактическая проверка и ограничения

Источники просмотрены через веб-поиск и страницы npm/GitHub/TC39. Команда `npm view @js-temporal/polyfill version engines dist-tags --json` завершилась `ENOTCACHED`: в этой среде npm работает с режимом `only-if-cached`, а запись пакета отсутствует в кэше. Установка пакета, TypeScript-проверка и исполнение DST-примеров пока не проводились. При реализации подтвердить поведение на закреплённой 0.5.1 в Node.js 24.21.0.
